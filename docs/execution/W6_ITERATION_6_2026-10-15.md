# W6 — Iteração 6: DNS pinning real no transporte HTTPS

**Data:** 15/10/2026. **Base:** checkpoint W6 Iteração 5 (179 testes).  
**Estado:** implementação e testes locais concluídos; validações externas e release ainda pendentes.

## Problema de segurança

A validação preflight de um hostname (`validate_destination`) rejeitava URL,
porta, credenciais e IPs privados, mas o `httpx` podia resolver o hostname
**uma segunda vez**, ao abrir o socket. Um DNS que respondia primeiro com
IP público e depois com loopback, RFC1918 ou serviço de metadados de nuvem
poderia contornar o preflight (TOCTOU/DNS rebinding).

## Mudanças

1. `network_guard.py`: `resolve_public_addresses` trata IP literal e todos os
   registros DNS (IPv4/IPv6), rejeitando o conjunto inteiro se estiver vazio,
   indisponível ou contiver endereço não global.
2. `PublicIPNetworkBackend`: o `httpcore` chama o backend **no instante de
   conectar**. Esse backend realiza novo DNS, valida todos os endereços e chama
   o socket do backend inferior **somente com um endereço IP numérico aprovado**.
   Se a primeira rota pública falhar, tenta os demais IPs públicos validados.
   Rejeita portas diferentes de 443, sockets Unix e override de endereço local.
3. `PinnedAsyncHTTPTransport`: injeta esse backend na pool HTTPS, mantém
   hostname original no nível HTTP/TLS (Host, SNI e validação do certificado),
   preserva limites de conexões e desabilita proxies/variáveis de ambiente.
4. `FetchEngine`: usa o novo transporte por padrão. `RobotsCache` compartilha
   o mesmo cliente, portanto `robots.txt` também usa a proteção.
5. Dependências `httpx` 0.28.x e `httpcore` 1.0.9–1.0.x restritas; isso é
   deliberado porque a substituição da pool usa a interface de integração entre
   as bibliotecas. O teste de contrato deve falhar após upgrades incompatíveis.

## Testes adicionados (7)

- IP público aprovado no socket, sem nova conexão usando o hostname DNS.
- Host HTTP e TLS/SNI continuam sendo o hostname original.
- DNS público no preflight que vira IP privado ao conectar: **não disca**.
- Resposta DNS mista (pública + privada): bloqueia tudo, sem tentativa.
- Falha da primeira rota pública: fallback restrito a outro IP público.
- Falha na resolução: fail-closed; bloqueio de IP privado, porta, Unix e local address.
- Verificação de que fonte e `robots.txt` compartilham o transporte protegido.

## Limitações e aceite pendente

- Os novos testes usam um socket simulado para verificar o destino da conexão,
  além de DNS simulado. **Não ocorreu teste egress/TLS/DNS contra redes reais.**
- É obrigatório testar DNS rebinding, redirecionamentos, conexões IPv4/IPv6,
  timeouts e comportamento real do proxy/firewall em staging com uma rede
  isolada. Bloquear egress para CIDRs locais/metadata **na infraestrutura**
  continua obrigatório (defesa em profundidade).
- Configurações alternativas de transporte HTTP fora do `FetchEngine` não
  adquirem automaticamente esta proteção. O fetcher padrão e `RobotsCache`
  estão integrados; consumidores legados precisam de revisão antes de uso
  com URLs não confiáveis.
- `ruff`, `mypy`, build Next.js, PostgreSQL real, Redis/Celery concorrente,
  testes de carga, disaster recovery real e E2E evento→alerta→UI **não foram
  executados neste ambiente**.
- `SOURCE_SCHEDULER_ENABLED=false` continua sendo o padrão. Não habilitar
  coleta periódica em produção nem declarar W6 aceita.
