# W6 — Iteração 3: scheduler adaptativo e regressão de fontes

**Data:** 2026-10-15. **Base:** checkpoint W6 Iteração 2 (135 testes). **Status:** implementação local verificada; integração de banco/worker/staging ainda aberta.

## Entrega

1. **Migração 0007** (`db/sql/0007_w6_source_operations.sql`): estado por fonte de próximo recrawl, prioridade, cadência, lease com token de fencing e cursor do último run processado. Estado de regressões por fonte + código, com último alerta e revisão vinculada. Migração Alembic suporta downgrade. Esquema analisado estaticamente: **74 tabelas**, 5 extensões.
2. **Manutenção persistida** (`hackathon_operations.source_maintenance`): avalia `crawl_runs` finalizados (até 5 recentes por fonte), frequência de alteração, datas futuras de eventos associados, prioridade/credibilidade e intervalo mínimo de fonte. Evita adiar um recrawl vencido quando não existe um run novo. Aplica backoff para falhas sequenciais. Atualiza saúde e datas da fonte somente após um novo run completo. `user_interest` fica em **0.0**, já que o interesse agregado por fonte ainda não está modelado.
3. **Anomalias**: compara execuções e abre itens `SOURCE_ANOMALY` na fila administrativa para `EVENT_COUNT_COLLAPSE`, `PARSER_ZERO_OUTPUT` e `HIGH_FAILURE_RATE`. Processamento idempotente pelo ID de crawl, com estado persistente para suprimir revisões duplicadas enquanto uma estiver aberta; uma revisão encerrada pode gerar nova revisão após cooldown de 24 h e novo run. As evidências incluem IDs dos dois crawls e a mensagem do sinal.
4. **Dispatcher opcional** (`hackathon_operations.dispatcher`): registra/atualiza sem rede as quatro integrações live conhecidas antes do planejamento (sem sobrescrever políticas do operador), e limita a execução a esses adaptadores; fonte deve estar ativa, aprovada (`ALLOWED`), com descoberta e extração habilitadas e modo permitido. `FOR UPDATE SKIP LOCKED` + token de lease de 30 minutos impedem duas reivindicações simultâneas. Antes da descoberta e de cada página, o runner valida licença, pausa e titularidade/validade da lease. O `FetchEngine` continua validando host, rede, robots (quando aplicável) e limite de taxa.
5. **Worker Celery**: `sources.maintenance_and_dispatch`, com agendamento de 15 em 15 minutos somente quando `SOURCE_SCHEDULER_ENABLED=true`. A configuração padrão é **false**. É necessário executar um processo Celery Beat separado; ativar a flag não inicia o Beat por si só.
6. **UI de operações** `/admin`: lista próximo recrawl, cadência, score, motivo e lease de cada fonte. A saúde `BROKEN` agora conta como degradada no resumo.
7. **Fail-closed**: upsert do registry não sobrescreve política operacional da fonte registrada no PostgreSQL. Runners persistidos e diagnóstico/REST consultam autorização no banco; falha de descoberta termina o crawl em `FAILED` em vez de deixá-lo `RUNNING`.
8. **CI de integração PostgreSQL**: `scripts/ops/source_maintenance_integration_check.py` em banco temporário depois do round trip Alembic. Exercita geração de duas anomalias, idempotência, saúde, pausa, permissão, reivindicação única e token incorreto. Ainda **não executado** localmente por falta de PostgreSQL.

## Como validar e operar

```bash
# Preparar ambiente e banco real/migrações:
pip install -e '.[dev]'
alembic -c db/alembic.ini upgrade head

# Manutenção sem rede (gera planos e revisões no banco):
DATABASE_URL='postgresql+psycopg://...' python scripts/ops/run_source_scheduler.py

# Coleta ativa, manual e explicitamente solicitada:
DATABASE_URL='postgresql+psycopg://...' python scripts/ops/run_source_scheduler.py --dispatch --limit 3 --max-pages 5

# Integração somente em banco EFÊMERO/CI, nunca no banco real:
APP_ENV=test HIP_ALLOW_SOURCE_DB_DRILL=1 DATABASE_URL='postgresql+psycopg://...' \
    python scripts/ops/source_maintenance_integration_check.py

# Automação Celery (dois processos gerenciados separadamente, com Redis ativo):
SOURCE_SCHEDULER_ENABLED=true celery -A hackathon_worker.app:celery_app worker -l info
SOURCE_SCHEDULER_ENABLED=true celery -A hackathon_worker.app:celery_app beat -l info
```

Em staging, configurar `SOURCE_SCHEDULER_BATCH_SIZE` (1–20) e `SOURCE_SCHEDULER_MAX_PAGES` (1–20), monitorar rate limit, HTTP e concorrência. Ativar agendamento apenas depois da aplicação e validação da migração 0007. **Não ativar o scheduler periódico em produção agora.** A execução manual `--dispatch` também emite rede real: usar apenas com permissão da fonte e controle de ambiente.

## Gates externos ainda abertos

- PostgreSQL real: migração upgrade/downgrade, `source_maintenance_integration_check.py` e ensaio com volume/concorrrência; a política deve permanecer restritiva durante coleta.
- Celery worker + Beat + Redis integrados: scheduling/duplicidade/retries sob múltiplos processos. Leases de 30 minutos não substituem heartbeat ou supervisão se um crawl durar mais que a lease (o runner detecta perda da lease antes de cada próxima página, mas não cancela requisição HTTP já em trânsito).
- Next.js: `npm install`, `npm run lint`, `npm run typecheck`, `npm run build` e navegação real no painel.
- Falhas de autenticação, SAST, DNS/egress, load test, DR real, e E2E evento→alerta→UI permanecem pendentes da W6. A manutenção atual recalcula as fontes uma a uma (N+1 consultas) e não agrega ainda engajamento por fonte.
