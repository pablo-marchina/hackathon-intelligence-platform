# Iteração 29 — coleta controlada com atribuição de resultados reais

**Base:** Iteração 28 (486 testes Python). **Data:** 22/10/2026.
**Estado:** implementação testada localmente; **PostgreSQL/HTTP E2E real ainda pendentes**. Não aprovado para produção.

## Objetivo

Unificar em uma execução auditável e limitada o caminho fonte permitida → HTTP com política → persistência por página → normalização da **mesma fonte** → medição de registros canônicos criados/vinculados/atualizados/rejeitados. Essa é uma ferramenta operacional opt-in, não uma ativação do scheduler nem a promessa de novos hackathons coletados.

## Mudanças

1. **`scripts/ops/controlled_catalog_ingestion.py`**: novo comando de uma fonte por execução. Sem `--apply` não acessa banco nem rede, apenas apresenta limites e pré-requisitos. O `--apply` exige simultaneamente `APP_ENV` explícito (`development`, `test` ou `staging`), `HIP_ALLOW_LIVE_INGESTION=1`, `DATABASE_URL`, fonte autorizada no seed, e autorização/ativação **vigentes no PostgreSQL antes da criação do cliente HTTP**. Revalida permissões antes de cada normalização. Nunca aceita `APP_ENV=production`.
2. **`CanonicalProcessor`**: parâmetro opcional `source_key` para selecionar somente registros daquela origem; o comportamento sem filtro permanece inalterado. Nova propriedade `last_outcome` diferencia `LINKED` de `UPDATED` nos diagnósticos sem alterar os valores de retorno legados. O filtro SQL tem cast explícito para parâmetros nulos no PostgreSQL.
3. **Métricas**: retorno com `crawl_run_id`, páginas buscadas, referências gravadas, versões normalizadas nesta execução, contagem por resultado **atribuída ao ID da coleta original**, e contagem de canônicos ativos antes e depois. **O delta de catálogo não é um indicador isolado de hackathons recém-anunciados**: outros workers podem escrever, e eventos históricos podem ser importados.
4. **Integração com CI**: novo teste `controlled_ingestion_integration_check.py` usando HTTP inteiramente simulado e banco PostgreSQL descartável. Exercita ingestão, canonização, idempotência e pausa do operador. Foi **adicionado ao CI, mas não executado com PostgreSQL** neste ambiente.
5. **Testes de segurança locais**: nenhum banco/rede sem `--apply`, bloqueio de fontes restritas, desconhecidas e sem URLs, orçamento de execução, recusa de produção, bloqueio por PostgreSQL e isolamento dos resultados.

## Comandos

Planejar sem conexões nem gravações:

```bash
python -m scripts.ops.controlled_catalog_ingestion --source hackclub_hackathons --max-pages 3 --max-versions 100
```

Somente após preparar *staging* e aplicar as migrações, confirmar que a fonte é permitida no cadastro **e** em `sources` no PostgreSQL:

```bash
APP_ENV=staging HIP_ALLOW_LIVE_INGESTION=1 DATABASE_URL='postgresql+psycopg://...' \
python -m scripts.ops.controlled_catalog_ingestion --source hackclub_hackathons \
  --max-pages 3 --max-versions 100 --apply
```

O comando pode acessar sites externos **somente se explicitamente autorizado**. Não execute em produção; mantenha os limites de rate/robots/hosts/TLS e confirme as permissões vigentes antes de testar. Não passe credenciais em flags de linha de comando. O relatório JSON vai para stdout e não contém senhas ou corpos HTTP.

Para rodar o exercício E2E com PostgreSQL descartável, somente em ambiente de teste:

```bash
APP_ENV=test HIP_ALLOW_CONTROLLED_INGESTION_DRILL=1 \
DATABASE_URL='postgresql+psycopg://hackathon:hackathon@127.0.0.1:5432/hackathon' \
python -m scripts.ops.controlled_ingestion_integration_check
```
